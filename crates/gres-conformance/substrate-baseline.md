# Substrate-backed engine baseline

The `gres-conformance` CI job runs the primary corpus twice: once against an in-process `crabka-gres` and once against a substrate-backed one (`--substrate-bootstrap`, whose WAL is a Kafka tenant topic on a live Crabka broker). This file explains why the second leg gates on `substrate-baseline.json` (6183/6198) rather than on the primary `baseline.json` (6192/6198), and enumerates every statement behind the difference. The number is a floor for one specific engine assembly, not a claim of parity with the in-process leg.

Fifteen statements mismatch here. Six of them are the primary leg's own slack — the same six statements `baseline.json`'s 6192 already accounts for — and belong to that file, not this one. The other nine mismatch only on the substrate leg, in two unrelated groups.

## The oracle-database artifact (1 statement)

`catalog_functions.sql` runs `SELECT current_database()`. The corpus never drops the relations it creates, so a second leg replayed against the same oracle database would accumulate rows and degrade parity for reasons that have nothing to do with the subject. CI therefore creates a fresh `oracle2` database for this leg and points the oracle at it. The oracle then answers `oracle2` while the subject answers `postgres`, which is the constant Gres returns from `current_database()` regardless of the connection.

This mismatch is a property of the harness, not of the subject: the same statement matches on the primary leg, where the oracle database *is* `postgres`. It is also why this leg can never reach the primary floor — even with the sequence gap below closed, the leg would measure 6191 against a floor of 6192. The sharded gate creates `gres_sharded_oracle` and carries `sharded-baseline.json` for the same structural reason.

## The replicated-sequence gap (8 statements)

A substrate-backed engine is built by `SqlEngine::replicated` (via `open_substrate_engine` → `build_replicated_substrate_engine` in `crates/gres/src/lib.rs`), which puts the counter managers in `PersistMode::Replicated`: a counter advance must ride the commit batch into the WAL rather than be written straight to the applied store. `SequenceManager::alloc` — the internal per-table rowid counter — does exactly that. The user-visible sequence path does not. In `crates/pgexec/src/seq.rs`, both `setval_written` and the private `advance` that backs `nextval`/`nextval_written` refuse outright under `PersistMode::Replicated`:

```
0A000  replicated SQL sequence updates are not wired yet
```

so every sequence advance is refused on this leg — `nextval`, `setval`, `SERIAL`, and both `GENERATED … AS IDENTITY` forms. `create_table_breadth.sql` is the only corpus file that advances a sequence, and it accounts for all eight statements: five refusals and the three follow-up `SELECT`s that then find no rows.

| Statement | Substrate outcome |
| --- | --- |
| `INSERT INTO ctb_id (b) VALUES ('one')` | `0A000` |
| `INSERT INTO ctb_id (b) VALUES ('two')` | `0A000` |
| `SELECT a, b FROM ctb_id ORDER BY a` | no rows |
| `INSERT INTO ctb_id (a, b) VALUES (100, 'explicit')` | `0A000` |
| `SELECT a, b FROM ctb_id ORDER BY a` | no rows |
| `INSERT INTO ctb_id2 (b) VALUES ('one')` | `0A000` |
| `INSERT INTO ctb_id2 (b) VALUES ('two')` | `0A000` |
| `SELECT a, b FROM ctb_id2 ORDER BY a` | no rows |

The fourth row is worth a second look: `ctb_id.a` is `GENERATED BY DEFAULT AS IDENTITY` and that `INSERT` supplies it, yet the refusal still fires — so the engine consumes a sequence value even when the column is written explicitly. PostgreSQL 18 does not, and the in-process engine's divergence is measurable there: insert `'one'`, then an explicit `100`, then `'three'`, and PostgreSQL generates `1` and `2` while Gres generates `1` and `3`. Neither leg catches it, because the corpus only reads the table back and never asks what the next generated value would be.

The corpus understates the gap. Eight statements is what this corpus happens to exercise; the missing feature is every sequence-backed default in the engine.

Closing it is a design, not a hookup — the manager is already constructed and shared with the substrate engine, and `reseed_counters` already calls into it. What is missing is (a) an in-memory replicated sequence cache so successive `nextval`s advance before the batch applies, invalidated on `DROP`/`CREATE` of the same name and on a writer-generation change, (b) a seam carrying staged ops out of synchronous expression evaluation into each commit batch, including for a read-only `SELECT nextval('s')`, which commits nothing today, and (c) a decision on whether a replicated advance keeps PostgreSQL's non-transactional `nextval` or follows `alloc` and rides the transaction. Getting (a) wrong hands out duplicate identity values after a failover.

Removing this baseline requires closing that gap and reconciling `current_database()` with the fresh-oracle requirement; until both hold, gating this leg on `baseline.json` would be a misconfiguration.
