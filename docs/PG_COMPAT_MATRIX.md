# PostgreSQL compatibility matrix for Chapter Gres

This matrix is the SQL-Parity Program anti-rot ledger. Every row has an explicit disposition; no row may be left undecided. `Wave-assigned(...)` means the command is intentionally not complete yet and names the parity wave that owns it. M5 is reached when no command row remains wave-assigned.

Published milestone state: [M0, 2026-07-11](superpowers/evidence/2026-07-11-gres-m0.md).

Run:

```bash
tools/check-pg-compat-matrix.sh --self-test
tools/check-pg-compat-matrix.sh
```

## Current G-1/G-2 baseline

The implemented rows reflect the current parser/executor surface. The
authoritative PostgreSQL 18.4 core-schedule score is 28 / 231 exact in serial
under the runner's explicit 20 MiB blocking-query memory policy, leaving 203
failures across 169627 changed lines and 4732 hunks. Both PostgreSQL
self-checks pass 231 / 231, Gres completes all 231 files with a successful
postflight probe and an empty infrastructure report. Parallel mode has not been
re-measured since the type-input wave; its last certified figure was 22 / 231 at
177530 changed lines / 4608 hunks.

These waves add `int4`, `int2`, `roleattributes`, `lseg`, `line` and `circle`
to the exact set (`+6` files, `-6374` changed lines) with zero newly failing files, by
implementing PostgreSQL's real integer input grammar — `0x`/`0o`/`0b` bases and
`_` separators — its exact out-of-range messages for every integer and float
width, general source positions for type-input errors, the optional `TABLE`
object-type keyword in `GRANT`/`REVOKE`, the `TABLE t` derived-table form, the
`int2vector`, `lseg`, `line` and `circle` types, and `ALTER ROLE` with persisted role attributes. Four files gain 22 lines between them
because a caret is now correctly attached to errors Gres should not raise at
all; those disappear with the underlying rejections. The checked-in monotone
floor remains 6 / 231 because 56 baseline fingerprints still worsen and 19
change at the same mismatch size even though 116 improve and 17 disappear; that
non-monotonicity predates this wave and the ratchet tool correctly refuses to
advance the floor through it.

The complete artifact certifies the focused `boolean` and `varchar` gains.
`sanity_check` remains a 5-line / 1-hunk failure after preceding schedule state
despite being exact in isolation, so its order-sensitive catalog residual is
still open. The prior serial measurement whose parallel run stopped at 92 /
231 remains non-certifying. Replay exposed a CPU-bound two-branch OR nested
loop rather than a lock cycle; bounded candidate union and direct INNER/LEFT
`count(*)` folding now make the isolated upstream query return `19000` in 0.30
seconds and reduce the complete serial `join` file from 294.320 seconds to
9.532. The full parallel schedule now completes, but an earlier three-branch
OR count in `join` still exceeds the memory budget and the 296.989-second
serial lateral `subselect` workload remains the cohort's performance root.

Within one active catalog, user-type registry publication is derived from the
committed catalog delta, after event-trigger acceptance, for TYPE/DOMAIN DDL,
schema cascades, temporary namespace cleanup, and savepoint rollback. Nested
trigger DDL re-reads final durable state, and rejected hooks publish the restored
delta, so a failed catalog change cannot leave a parser-visible type name that
durable `pg_type` does not contain. The process registry is not yet scoped by a
stable catalog identity; independent `SqlEngine` catalogs can allocate the same
local OID and overwrite one another's global registry entries. Type cascade
closure also does not yet cover every non-type dependent: dropping a type or
schema with `CASCADE` can leave a table outside that schema whose column still
references the removed type OID.

Full-text search includes first-class `tsvector`/`tsquery` values (OIDs 3614/3615), casts and persistence, English/simple normalization, weighted positions, query and phrase operators, conversion/manipulation/ranking/headline functions, `jsonb_to_tsvector`, `default_text_search_config`, durable configuration/dictionary DDL, catalog rows, and durable local GIN posting indexes over stored `tsvector` columns with MVCC heap rechecks. Expression/multicolumn/global/sharded GIN indexes, text-search arrays, and byte-identical PostgreSQL ranking/headline algorithms remain deferred; parser/template DDL remains a C-bound non-goal. This paragraph supersedes older per-type deferral notes below.

## Owner and process

- **Owner:** Chapter Gres SQL-Parity Program.
- **Update rule:** every wave that changes SQL acceptance or semantics updates this file in the same change.
- **Inventory rule:** [`pg18-command-inventory.json`](pg18-command-inventory.json) is derived solely from hashed `REL_18_0` SGML artifacts: the SQL entity list plus the `ALTER TABLE`, `CREATE TABLE`, and `SELECT` synopses. The deterministic extraction expands PostgreSQL's abbreviated entity filenames and extracts the seven additional syntax-family titles directly from those synopses, yielding exactly 190 unique titles. Major language features remain a separate typed manifest and never count as commands.
- **Anti-rot rule:** parser acceptance is owned by the typed `CommandIdentity` dispatch registry and gated at every public parse boundary. `tools/check-pg-compat-matrix.sh` checks that registry, inventory, command rows, behavior probes, and the separate major-feature manifest in both directions, then runs executable representatives through an in-memory SQL session. Refusals assert exact SQLSTATE plus a stable message fragment.
- **Bounded-refusal rule:** architectural `Non-goal(...)` rows recognize the representative PostgreSQL 18 syntax recorded in typed parser metadata and fail through the ordinary session path with `0A000`; unrecognized or trailing syntax is never swallowed by a prefix-only matcher.
- **Allowed dispositions:** `Implemented`, `Wave-assigned(<wave>)`, `Mapped(<semantics>)`, `Error-with-notice(<SQLSTATE>)`, `Non-goal(<reason>)`.

| ALTER TABLE | Implemented | The full ordinary-table subcommand family, including the multi-subcommand comma form (one atomic batch) and `IF EXISTS`/`ONLY`. `ADD [COLUMN] [IF NOT EXISTS]` (with `DEFAULT`, `NOT NULL`, `CHECK`, `PRIMARY KEY`, `UNIQUE`), `DROP [COLUMN] [IF EXISTS] [CASCADE|RESTRICT]`, `ALTER [COLUMN] … SET/DROP NOT NULL`, `SET/DROP DEFAULT`, `[SET DATA] TYPE … [USING expr]`, `ADD [CONSTRAINT n] {CHECK|UNIQUE|PRIMARY KEY|FOREIGN KEY} [NOT VALID]`, `DROP CONSTRAINT [IF EXISTS]`, `RENAME [COLUMN] … TO`, `RENAME CONSTRAINT`, `RENAME TO`, `VALIDATE CONSTRAINT`, `SET (…)`/`RESET (…)`, and `OWNER TO`. Add/drop/type changes rewrite the table's stored row versions inside the same DDL batch (DDL holds the global catalog lock), so `ADD COLUMN … DEFAULT` back-fills like PostgreSQL's missing value and `DROP COLUMN` reclaims the position rather than tombstoning it. Every back-validation and index backfill reads the batch's *rewritten* rows, so a constraint attached to a column the same statement just added is checked against the back-filled values. `ADD CONSTRAINT CHECK` and `SET NOT NULL` back-validate live rows all-or-nothing (`23514` "is violated by some row" / `23502` "contains null values"); `NOT VALID` skips that scan, records `pg_constraint.convalidated = false`, and still governs every subsequent write, with `VALIDATE CONSTRAINT` running the skipped scan and flipping the flag. `ADD PRIMARY KEY` builds the unique index first, so duplicate data is `23505` ("could not create unique index") ahead of the NULL check's `23502`, matching PostgreSQL's order; it then marks the key columns NOT NULL. `NOT VALID` is refused for `PRIMARY KEY`/`UNIQUE` (`0A000`, as in PostgreSQL: an index-backed constraint has to be built now). `ALTER COLUMN … TYPE` coerces in PostgreSQL's *assignment* context — a cast that is explicit-only (`text → int4`, `bool → int4`) is `42804` "cannot be cast automatically" unless `USING` is given, and an unknown target type name is `42704`. The rewrite casts only rows that are still live (a value already deleted or updated away cannot block it), re-encodes every index over the column so index scans and unique enforcement stay correct across the change, and re-analyzes the table's stored `CHECK` predicates, failing the statement (e.g. `42883` "operator does not exist") rather than committing a table that rejects every write. One statement may not retype the same column twice (`0A000`). `RENAME COLUMN` and `RENAME TO` rewrite their dependencies: stored `CHECK` predicates and index column lists are rewritten structurally, and stored view text is rewritten token-wise under catalog resolution — a rename is refused with `0A000` naming the view only when the catalog cannot prove the reference unambiguous (an unresolvable FROM item, another referenced relation owning a column of the old or new name, a relation reference outside a `FROM`/`JOIN` slot or an unaliased `<table>.<column>` qualifier, or a reference written as a *quoted* identifier, whose source span the token rewrite cannot substitute), so a view can never silently change meaning and an *unrelated* view never blocks a rename. `DROP COLUMN`, `ALTER COLUMN … TYPE`, and `DROP TABLE` honour PostgreSQL's per-column view dependencies: dropping a column no view reads is allowed, dropping one a view reads is `2BP01` (`CASCADE` drops the dependent views instead), and retyping one a view reads is `0A000` "cannot alter type of a column used by a view or rule". A `GENERATED ALWAYS AS (…) STORED` column depends the same way on every column its expression reads: retyping one of those is `0A000` "cannot alter type of a column used by a generated column" and dropping one is `2BP01`, with `CASCADE` taking the generated column too. A subcommand aimed at a view names the action in PostgreSQL's 42809 ("ALTER action ADD COLUMN cannot be performed on relation …") rather than reporting a missing relation. `ADD [CONSTRAINT n] FOREIGN KEY (…) REFERENCES …`, and the column-level `REFERENCES` spelling on `ADD COLUMN`, resolve and enforce exactly as `CREATE TABLE`'s do (see that row for the constraint surface, the DDL SQLSTATEs and the DML semantics), and back-validate the table's live rows with `23503` and the ordinary row-write message when a stored row has no parent; `NOT VALID` skips that scan, records `convalidated = false` and still governs every later write, and `VALIDATE CONSTRAINT` runs the skipped scan and flips the flag. Back-validation reads the batch's rewritten rows like every other one, so `ADD COLUMN a int4 DEFAULT 5, ADD CONSTRAINT … FOREIGN KEY (a) REFERENCES p` validates the back-filled default, and a self-referencing key resolves against the statement's staged catalog. `DROP CONSTRAINT [IF EXISTS] [CASCADE]` and `RENAME CONSTRAINT` handle foreign keys (the rename re-keys the catalog record, because a constraint's catalog key carries its name), `RENAME COLUMN` rewrites both column lists — an `ON DELETE SET` column list and a self-reference's referenced side included — and `DROP COLUMN` drops any foreign key keyed on that column, while a column some foreign key *references* is `2BP01`, because the unique index proving it a key cannot go. `{ENABLE|DISABLE|FORCE|NO FORCE} ROW LEVEL SECURITY` move the relation's row-security flags (see the `ALTER TABLE ENABLE ROW LEVEL SECURITY` row). `SET SCHEMA`/`SET TABLESPACE`/`SET LOGGED`/`CLUSTER ON` and the trigger subcommands parse and fail clear with `0A000` naming the subcommand. `ADD PRIMARY KEY`/`UNIQUE` on sharded tables still fail clear `0A000` until global enforcement exists. The column-shape subcommands — `ADD COLUMN`, `DROP COLUMN`, `RENAME COLUMN`, `ALTER COLUMN … TYPE`, `SET`/`DROP NOT NULL` and `SET`/`DROP DEFAULT` — recurse to *every* descendant, walking the partition tree and the inheritance DAG together in one visited-set traversal, so a relation reachable by two paths (a diamond's foot) is altered once and a grandchild is altered at all. Each descendant repeats the subcommand against its own catalog record and its own stored rows; an added column is copied from the shape the named relation ended up with, so a child never independently re-resolves the `ColumnDef` (one `serial`'s sequence, not one per child), and a descendant that already declares the name *merges* when the types agree and is `42804` "child table \\"c\\" has different type for column \\"x\\"" when they do not. `ONLY` suppresses the recursion, and is refused exactly where PostgreSQL refuses it, with `42P16`: `ADD COLUMN` whenever any descendant exists ("column must be added to child tables too"), `RENAME COLUMN` and `ALTER COLUMN … TYPE` likewise ("inherited column \\"x\\" must be renamed / type of inherited column \\"x\\" must be changed in child tables too"), and `DROP COLUMN`/`SET NOT NULL` only for a partitioned table ("cannot drop column from only the partitioned table when partitions exist" / "constraint must be added to child tables too", both with PostgreSQL's `HINT: Do not specify the ONLY keyword.`); on an inheritance parent those last two are local changes and are allowed. Not yet recursed: `ADD`/`DROP CONSTRAINT`, and `pg_attribute.attislocal`/`attinhcount` remain hardcoded `true`/`0`, so a merged column is indistinguishable from a locally-declared one and `ALTER TABLE … NO INHERIT` cannot restore it. Divergences: PostgreSQL's `NOTICE` for a skipped `IF EXISTS`/`IF NOT EXISTS` subcommand (and for a `CASCADE` drop) is not emitted, and the `DETAIL:` line of the `23514`/`23502`/`23505`/`2BP01` errors is omitted (message and SQLSTATE match); `DROP COLUMN` of a table's last remaining column is `0A000` where PostgreSQL creates a zero-column relation, because every read path here assumes at least one column; and a later subcommand sees the columns an earlier one added, so `ADD COLUMN c …, ALTER COLUMN c TYPE …` succeeds where PostgreSQL plans the type change against the pre-statement schema and reports `42703`. `DROP COLUMN` of a column a foreign key references reports `cannot drop index <index> because other objects depend on it` where PostgreSQL names the column (`cannot drop column id of table dp …`); the SQLSTATE (`2BP01`), DETAIL and HINT match, and `CASCADE` drops the referencing constraint either way. `ALTER CONSTRAINT` is not in the grammar, so `ALTER TABLE t ALTER CONSTRAINT c DEFERRABLE` reaches the ordinary unsupported-subcommand `0A000` naming `ALTER COLUMN`: a constraint's deferrability is fixed at definition time, and only `SET CONSTRAINTS` moves it per transaction. All four subcommands — `{ENABLE\|DISABLE\|FORCE\|NO FORCE} ROW LEVEL SECURITY` — projecting as `pg_class.relrowsecurity`/`relforcerowsecurity` and `pg_tables.rowsecurity`. While enabled, every read of the relation is filtered by the policies applicable to the session's role, and every write is: `UPDATE`/`DELETE` may only act on rows the `USING` qual admits (silently, as in PostgreSQL), and `INSERT`/`UPDATE` rows are judged by `WITH CHECK` *after* `BEFORE ROW` triggers have returned their replacement row (`42501` "new row violates row-level security policy …"). A relation with row security and no applicable policy shows no rows: permissive policies OR from a `FALSE` seed and restrictive ones AND onto the result. The owner bypasses its own policies until `FORCE`; `SUPERUSER` and `BYPASSRLS` bypass regardless. With `row_security = off` a statement a policy would have filtered fails with `42501` rather than returning a filtered result. `COPY … FROM` into such a relation is refused before the statement runs (`0A000`, PostgreSQL's "COPY FROM not supported with row-level security"); `COPY … TO` is refused by the grammar. Sharded relations are refused (`0A000`): their writes go through the timestamp path, which cannot evaluate a policy qual. A view's body is filtered by the *view owner's* policies unless the view was written `WITH (security_invoker)`, in which case the caller's apply (see the `CREATE VIEW` row). Divergence: `\d`/`pg_policies` report the qual's source text rather than PostgreSQL's deparsed form. |

See the `CREATE POLICY` row for what the flags then gate. |

| ALTER VIEW | Implemented | `ALTER VIEW [IF EXISTS] name { OWNER TO role | SET (option = value, …) | RESET (option, …) }`, owner-only (`42501` `must be owner of view <name>`), with the same role validation `ALTER TABLE … OWNER TO` applies (`CURRENT_USER`/`USER` resolve to the session's role; `PUBLIC` and an unknown name are `42704`). `OWNER TO` moves the identity the view's body runs under, so it changes which rows the view shows and which relations it may reach (see the `CREATE VIEW` row). `SET`/`RESET` move the `security_invoker` and `security_barrier` reloptions — the same closed option set `CREATE VIEW … WITH (…)` accepts, so an unrecognized name is the same `22023` `unrecognized parameter` in both spellings — and `check_option` is accepted and dropped in both. `ALTER VIEW` on a relation that is not a view is `42809` `"…" is not a view`. Not implemented: `RENAME TO`, `SET SCHEMA`, and the `ALTER [COLUMN] … SET/DROP DEFAULT` family, which reach a syntax error naming the subcommands that are supported rather than being consumed and ignored. |
| ANALYZE | Mapped(accepted hint) | The whole `ANALYZE [ ( option … ) ] [VERBOSE] [ table [ ( column, … ) ] [, …] ]` tail is parsed for shape and discarded; the command returns `ANALYZE`. There are no planner statistics to collect — Gres has no cost-based planner — so the command has nothing to do. Divergences: relation names are **not** resolved, so `ANALYZE no_such_table` succeeds where PostgreSQL raises 42P01; `pg_class.reltuples` remains `-1`, and `relhassubclass` remains false instead of acting as PostgreSQL's persisted, potentially stale, ANALYZE-maintained hint. |
| BEGIN | Implemented | `BEGIN [WORK|TRANSACTION] [ISOLATION LEVEL { SERIALIZABLE | REPEATABLE READ | READ COMMITTED | READ UNCOMMITTED }]`. An omitted level takes `default_transaction_isolation`, and `SHOW transaction_isolation` reports the level the block is actually running at. `READ UNCOMMITTED` runs as `READ COMMITTED` and still reports itself, exactly as in PostgreSQL. Divergences: `SERIALIZABLE` parses but is refused with `0A000` rather than silently answered by a weaker level, because there is no anomaly detection to back it (this also makes `BEGIN` fail while `default_transaction_isolation` is `serializable`); `BEGIN` inside a block is a silent no-op, without PostgreSQL's `WARNING: there is already a transaction in progress`; The `READ ONLY`/`READ WRITE`/`[NOT] DEFERRABLE` transaction modes are accepted in any order, with the commas optional, and mixed with `ISOLATION LEVEL`. An omitted access mode takes `default_transaction_read_only`, and `SHOW transaction_read_only` reports the mode the block opened with. A `READ ONLY` block refuses every statement that would change rows or catalog state with 25006 `cannot execute <command> in a read-only transaction`, and — being an ordinary statement error — that refusal aborts the block. `DEFERRABLE` is parsed and recorded but has no effect, since it only matters for a SERIALIZABLE READ ONLY transaction and SERIALIZABLE is refused. Divergence: PostgreSQL exempts writes to temporary tables from the read-only check; crabka's check keys on the statement kind and never resolves its target, so a write to a temporary relation is refused along with the rest. |
| CALL | Implemented | `LANGUAGE sql` procedures keep the existing statement-list execution and argument-substitution limits. `LANGUAGE plpgsql` procedures run the native interpreter, apply input defaults, preserve unknown-literal overload resolution, and return one result row for `OUT`/`INOUT` parameters. A top-level PL/pgSQL call and a pure nested `CALL` stack may `COMMIT` or `ROLLBACK` and start a fresh transaction afterward. Transaction control is rejected through an intervening function/query invocation, while an exception block is active, or from a `SECURITY DEFINER`/per-routine `SET` procedure. Divergences: SQL-procedure output parameters are not returned; `SECURITY DEFINER` and per-routine `SET` metadata are recorded but not applied during execution. |
| CHECKPOINT | Mapped(accepted hint) | Returns `CHECKPOINT`. Durability is the replicated log's, and checkpoint/compaction is driven autonomously by the storage layer, so there is no user-triggerable checkpoint to force. Unlike PostgreSQL there is no superuser check, because roles are not enforced yet. |
| CLOSE | Implemented | `CLOSE name` and `CLOSE ALL`. Closing a cursor that is not open is 34000 with PostgreSQL's message. The command tag follows the spelling, as PostgreSQL's does: `CLOSE CURSOR` for a named cursor and `CLOSE CURSOR ALL` for the whole set. |
| CLUSTER | Mapped(accepted hint) | `CLUSTER [ ( option … ) ] [VERBOSE] [ table [ USING index ] ]` is parsed for shape and returns `CLUSTER`. Physical row order is not user-controllable in an MVCC-over-KV store, so there is nothing to cluster. Divergence: names are not resolved, so `CLUSTER no_such_table` succeeds where PostgreSQL raises 42P01, and `CLUSTER t` on a table with no clustering index does not raise PostgreSQL's 55000. |
| COMMENT | Implemented | `COMMENT ON {TABLE|VIEW|COLUMN|INDEX|SEQUENCE} <name> IS {'text'|NULL}` persists (or, for `NULL`, clears) the comment in the catalog; the comment follows the object through `ALTER TABLE … RENAME TO`/`RENAME COLUMN`. A missing object raises PostgreSQL's SQLSTATE for that kind: `42P01` "relation … does not exist" for a table, view, index, or sequence — an index and a sequence *are* relations, so PostgreSQL reports the relation lookup, not an index- or sequence-specific message — and `42703` for a missing column of a relation that exists. Other object kinds fail clear with `0A000`. Divergence: the stored comment is not yet queryable through `obj_description`/`col_description`, so it is write-only from SQL. |
| COMMIT | Implemented | `COMMIT`/`END [WORK|TRANSACTION] [AND [NO] CHAIN]`. `AND CHAIN` commits and immediately opens another block with the same isolation level; outside a transaction block it is 25P01 (`COMMIT AND CHAIN can only be used in transaction blocks`) and changes nothing. `COMMIT` of an aborted block reports `ROLLBACK`, and chains from there too. Divergence: a plain `COMMIT` outside a block succeeds with tag `COMMIT` but does not emit PostgreSQL's `WARNING: there is no transaction in progress` — the wire layer has no `NoticeResponse` path yet. |

| CREATE TABLE | Implemented | Baseline table creation plus column `NOT NULL`/`NULL`, constant/simple-expression `DEFAULT`, `SERIAL`/`BIGSERIAL`, local-table `PRIMARY KEY`/`UNIQUE` (named or default-named), `IF NOT EXISTS`, an empty column list, `(LIKE source [INCLUDING …])`, `TEMP`/`TEMPORARY`/`UNLOGGED`/`GLOBAL`/`LOCAL`, `ON COMMIT PRESERVE ROWS`, and the `WITH (storage_parameter …)`/`WITHOUT OIDS`/`TABLESPACE` tails (accepted and ignored). `CHECK` constraints are now persisted as source text and enforced on INSERT/UPDATE/COPY with `23514` and PostgreSQL's message and default constraint naming (`<table>_<column>_check` when the predicate references one column, `<table>_check` otherwise, numeric-suffixed on collision); an explicit `CONSTRAINT <name>` that collides with a name already assigned in the same statement is `42710` "check constraint … already exists". Each predicate is analyzed when the table is created, exactly as PostgreSQL does at parse analysis: an unknown column is `42703`, a subquery is `0A000`, a non-boolean result is `42804`, an aggregate is `42803`, and a comparison whose operand types resolve to no operator is `42883` — so a table can never be created carrying a `CHECK` that fails every later write. The SQL three-valued rule is matched, so a NULL predicate passes. `GENERATED { ALWAYS | BY DEFAULT } AS IDENTITY [(sequence options)]` desugars onto a sequence-backed NOT NULL default, and `GENERATED ALWAYS AS (expr) STORED` is computed on every write before NOT NULL and CHECK; the expression is analyzed at DDL time and may read only plain stored columns of the same row, so reading another generated column is `42P17`, an unknown column `42703`, and an aggregate `42803`. Column-level `REFERENCES parent [(cols)] [MATCH …] [ON DELETE …] [ON UPDATE …]` and table-level `[CONSTRAINT n] FOREIGN KEY (cols) REFERENCES …` are enforced. Multi-column keys, self-references (the in-flight relation resolves against its own columns and indexes) and an omitted referenced-column list (which takes the parent's primary key, in index order) all work, and the default name is PostgreSQL's `<table>_<column…>_fkey`, numeric-suffixed on collision. The referenced columns must be covered by a unique index — a `PRIMARY KEY`, a `UNIQUE` constraint, or a bare `CREATE UNIQUE INDEX`, preferred in that order — otherwise `42830` "there is no unique constraint matching given keys for referenced table". The definition is analyzed when the constraint is created, with PostgreSQL's SQLSTATEs: a missing referenced relation is `42P01`, a view/sequence/foreign table `42809` "referenced relation … is not a table", a column-count disagreement or a repeated referenced column `42830`, an unknown column on either side `42703` "column … referenced in foreign key constraint does not exist", a key pair whose types are not comparable `42804` "foreign key constraint … cannot be implemented" with PostgreSQL's `Key columns "a" of the referencing table and "id" of the referenced table are of incompatible types: text and integer.` DETAIL, a column named by `ON DELETE SET NULL (…)`/`SET DEFAULT (…)` that is not part of the key `42P10`, and a constraint name already used on the relation `42710`. All five referential actions — `NO ACTION` (the default), `RESTRICT`, `CASCADE`, `SET NULL`, `SET DEFAULT` — are implemented on both `ON DELETE` and `ON UPDATE`, with `MATCH SIMPLE` (the default) and `MATCH FULL`; `MATCH PARTIAL` is `0A000`, as it is in PostgreSQL, and so is a column list on an `ON UPDATE SET …`, which PostgreSQL's grammar also confines to `ON DELETE`. `SET DEFAULT` evaluates the column's default, so a `nextval` default has its side effect. Checks fire once at the end of the statement rather than per row, exactly as PostgreSQL's AFTER-ROW triggers do, so `INSERT INTO t (id, boss) VALUES (1, 1)` against a `NOT DEFERRABLE` self-reference succeeds, a multi-row `VALUES` may reference a row it is inserting, and a data-modifying `WITH` succeeds whichever side it writes first; an `UPDATE` that leaves the key values alone, and a row `ON CONFLICT DO NOTHING` skipped, queue nothing. A referencing row whose key is absent is `23503` `insert or update on table "c" violates foreign key constraint "c_a_fkey"` with `Key (a)=(10) is not present in table "p".` — the same message on every write path (INSERT, UPDATE, COPY, MERGE, `ON CONFLICT DO UPDATE`, and `ALTER TABLE` back-validation), as in PostgreSQL — and a `MATCH FULL` key mixing NULL and non-NULL gets that message with PostgreSQL's `MATCH FULL does not allow mixing of null and nonnull key values.` DETAIL instead. A parent delete, or a parent update of the referenced values, that a child still references is `23503` `update or delete on table "p" violates foreign key constraint "c_a_fkey" on table "c"` with `Key (id)=(1) is still referenced from table "c".` under `NO ACTION`, and `23001` `update or delete on table "p" violates RESTRICT setting of foreign key constraint "c_a_fkey" on table "c"` with `Key (id)=(1) is referenced from table "c".` under `RESTRICT` — PostgreSQL's two distinct SQLSTATEs and wordings. The two behave identically while immediate and diverge only under deferral: `NO ACTION` re-probes at `COMMIT` and accepts a key a later statement re-supplied (PostgreSQL's `ri_Check_Pk_Match`), while `RESTRICT` never defers. `DEFERRABLE`/`INITIALLY DEFERRED`/`INITIALLY IMMEDIATE` are honoured for foreign keys: a deferred check is evaluated at `COMMIT` before the commit is recorded, so a violation fails the `COMMIT` and no row becomes visible, and `SET CONSTRAINTS` moves a constraint either way mid-transaction (see that row). Only *checks* ever defer, never referential actions — matching PostgreSQL, whose `RI_FKey_cascade_del`/`_setnull_del`/`_setdefault_del`/`_restrict_del` triggers are created non-deferrable while the check and `NO ACTION` triggers are deferrable — so a `DEFERRABLE INITIALLY DEFERRED ON DELETE CASCADE` still deletes its children inside the `DELETE`. Both sides lock the referenced key under the identity the uniqueness check already locks: the child side `Shared`, the parent side `Exclusive` and only when the referenced values actually change, so many children of one parent key never contend and a parent `UPDATE` that touches no key column takes no key lock at all — PostgreSQL's `FOR KEY SHARE` property without a third lock mode. `pg_constraint`, `pg_get_constraintdef` and the four constraint `information_schema` views describe every foreign key (see those rows). `DEFERRABLE`/`INITIALLY …` on the other constraint kinds — `CHECK`, `PRIMARY KEY`, `UNIQUE` — are still accepted and ignored, because only a foreign-key check can be queued; `information_schema.table_constraints` reports `is_deferrable`/`initially_deferred` as `NO`/`NO` for them. `NO INHERIT`/`ENFORCED` are accepted and ignored on every kind. Foreign-key divergences: a foreign key with a sharded or partitioned relation on either side is `0A000` ("foreign key constraint … on a sharded table is not supported" / "… on a partitioned table is not supported"), because cross-range enforcement is a later phase; type compatibility is decided by type *family*, so `int2`/`int4`/`int8` interoperate as they do in PostgreSQL but so do `text`/`varchar`/`char`, accepting a `text` ↔ `bpchar` pair PostgreSQL's opfamily rule would reject (while `integer` ↔ `numeric` is still `42804`); and no index is created for a foreign key, so a parent-side search falls back to a full scan of the child unless some child index's column set is a permutation of the key's — a leading-prefix index does not help, because the index encoding length-prefixes the whole tuple. `NOT VALID` is accepted and ignored *in `CREATE TABLE`* — which is what PostgreSQL does, since a brand-new table has no existing rows whose validation could be skipped, and the constraint is recorded `convalidated = true`. In `ALTER TABLE … ADD CONSTRAINT` it is honoured (see that row); PostgreSQL does not ignore it there. `TEMP`/`TEMPORARY` creates a real per-session temporary relation in a `pg_temp_<backend id>` namespace, which sits FIRST in the resolution order — ahead of the implicit `pg_catalog` — so `current_schemas(true)` reports `{pg_temp_7,pg_catalog,public}`. The shadowing is total, including `DROP`: with a permanent `public.shad` and a temporary `shad`, `INSERT INTO shad` hits the temporary one, `SELECT x FROM public.shad` reads the permanent one, and an unqualified `DROP TABLE shad` drops the TEMPORARY one and leaves the permanent one visible. `pg_class.relpersistence` is `t` for the table and for the indexes and `serial` sequences beside it, all of which live in the same namespace. `CREATE TABLE pg_temp.t` creates a temporary relation without the keyword, and so does a `CREATE TABLE` whose `search_path` creation slot is `pg_temp`. `CREATE TEMP TABLE s.t` naming an ordinary schema is `42P16 cannot create temporary relation in non-temporary schema`, and naming another session's namespace is `42P16 cannot create relations in temporary schemas of other sessions`. `ON COMMIT PRESERVE ROWS`/`DELETE ROWS`/`DROP` are all implemented, and outside an explicit block each statement is its own transaction, so `CREATE TEMP TABLE t (…) ON COMMIT DROP` leaves nothing behind — as in PostgreSQL. `ON COMMIT` on a permanent table is `42P16 ON COMMIT can only be used on temporary tables`. A foreign key may not cross the temporary/permanent line in either direction: `42P16 constraints on permanent tables may reference only permanent tables` and `42P16 constraints on temporary tables may reference only temporary tables`. The relations go at `DISCARD TEMP`, at `DISCARD ALL`, and when the connection ends; a backend that died without reaching that point leaves them until the next session drawing the same backend id purges the namespace before it uses it. Temporary divergences: another session cannot resolve the relation BY NAME, and `information_schema.tables`/`.columns` hide it as PostgreSQL's `pg_is_other_temp_schema` filter does, but a deliberate `SELECT * FROM pg_temp_7.t` from another session on the same node reads the rows, where PostgreSQL reads none (its pages are in the owning backend's local buffers); DDL is not transactional here, so an `ON COMMIT DROP` issues its catalog batch after the data commit rather than as part of it, and a `CREATE TEMP TABLE` survives a `ROLLBACK`. `UNIQUE NULLS NOT DISTINCT` parses and fails clear with `0A000`; PostgreSQL's `NOTICE` on a skipped `IF NOT EXISTS` is not emitted; identity columns do not reject a non-DEFAULT value for `GENERATED ALWAYS` (`428C9`) and accept it like `BY DEFAULT`. SERIAL ownership/drop dependency details are not implemented. |

| GRANT | Implemented | `GRANT priv[, …] ON [TABLE] rel TO grantee[, …]` writes the grants the executor now gates data access on: a role that holds none is refused with `42501` `permission denied for table <name>`, or `permission denied for view <name>` when the relation is a view. `SELECT` needs `SELECT`, `INSERT` needs `INSERT`, `UPDATE` needs `UPDATE`, `DELETE` needs `DELETE`, `TRUNCATE` needs `TRUNCATE`; an `UPDATE`/`DELETE` additionally needs `SELECT` when it reads a column of its own target — a `WHERE` naming a target column, a `RETURNING` of one, or a self-referencing assignment — while a `WHERE` that reads only a joined relation does not, which is PostgreSQL's `selectedCols` rule; `MERGE` needs `UPDATE` and `SELECT`. The bypasses are PostgreSQL's, in PostgreSQL's order: a superuser, the relation's owner (matched by role membership, not by name equality, so a member of an owning group owns it too), a grant naming the role, a grant to `PUBLIC`, and a grant to a role whose privileges the role holds. `ON` names a *relation*, so a view is grantable in its own right and carries its own owner and ACL, checked before its body runs — and, because the body then runs with the *owner's* rights, that check is the only thing standing between the caller and everything the view can reach, so it is never skipped. A non-owner needs a grant on the view and nothing else; the view's owner needs the grants on whatever the body reads. A `security_invoker` view keeps the older shape: the caller needs both. See the `CREATE VIEW` row. | Common table expressions and WITH RECURSIVE | Implemented | Several `WITH` items evaluated once each in list order, an item reading an earlier one, column alias lists (a list SHORTER than the query is legal and leaves the trailing columns their own names, as in `PostgreSQL`), `MATERIALIZED` / `NOT MATERIALIZED` (accepted and ignored — an inlining hint that cannot change rows, and this executor always materializes), and CTEs inside subqueries, derived tables and set-operation branches. `WITH RECURSIVE` runs `PostgreSQL`'s fixpoint: the non-recursive term seeds a working table and the recursive term re-runs against each round's output until a round is empty, with `UNION` additionally dropping rows already produced. The split is at the top-level `UNION`, so the non-recursive term may itself be a `UNION`; the item list is topologically sorted so a recursive item may read one declared later, and a true cycle is `PostgreSQL`'s `0A000` "mutual recursion between WITH items is not implemented". `PostgreSQL`'s well-formedness rules are enforced with `42P19`: a body that is not `non-recursive-term UNION [ALL] recursive-term`, a self-reference in the non-recursive term, more than one self-reference, one inside an expression subquery (a scalar subquery, `EXISTS`, `IN` or a quantified comparison) or on the nullable side of an outer join, and an aggregate in the recursive term. A FROM-clause sub-SELECT is *not* a subquery for that rule — `PostgreSQL` restricts SubLinks, not derived tables — so `SELECT n + 1 FROM (SELECT n FROM t) q` is legal and its self-reference is the term's one top-level reference. The aggregate ban is scoped the way `PostgreSQL` scopes it: to the query level that HOLDS the self-reference, not to the recursive term as a whole. An aggregate one level ABOVE the self-reference is legal (`SELECT max(n) + 1 FROM (SELECT n FROM t) q`), and one in the select list or `HAVING` of the level holding it is `42P19` however deeply nested that level is (`SELECT n + 1 FROM (SELECT max(n) AS n FROM t) q`); `GROUP BY`, `DISTINCT` and window functions at that level are not aggregation for this rule. `ORDER BY`/`LIMIT`/`OFFSET` on the recursion itself is `0A000` as in `PostgreSQL`, a column-count mismatch across the `UNION` is `42601`, an alias list longer than the query is `42P10`, a duplicate item name is `42712`, and a forward reference in a plain (non-`RECURSIVE`) `WITH` is `42P01`. The recursive term is type-checked before the first round, exactly as `PostgreSQL`'s `analyzeCTE` does: the non-recursive term fixes each column's type and the `UNION`'s common type must equal it, so a term that widens a column is `42804` ("recursive query \"t\" column 1 has type integer in non-recursive term but type numeric overall") and one whose type will not unify at all is `42804` ("UNION types integer and text cannot be matched") — neither runs a single round. A bare `NULL` or string literal in the recursive term is `PostgreSQL`'s `unknown` and adopts the seeded type instead, so `SELECT 1 UNION ALL SELECT 'x' FROM t` is well-typed and fails at run time with the cast's own `22P02`. Divergence: an unterminated recursion is bounded — the accumulated result is subject to the blocking-query memory budget (`53200`) and the iteration count is capped at 100 000 (`54001`) — where `PostgreSQL` runs until the backend exhausts memory or the statement is cancelled, so a query such as `WITH RECURSIVE t(n) AS (SELECT 1 UNION ALL SELECT n FROM t GROUP BY n) SELECT n FROM t` fails here and hangs there. `SEARCH`/`CYCLE` have their own row. Data-modifying items (`WITH d AS (DELETE … RETURNING …) …`) run exactly once each whether or not anything reads them, and every part of the statement — each item and the body — reads the one statement snapshot, so none of them sees another's rows.
