# Crabka North-Star Vision — One Columnar Substrate, Four Faces, plus a Serverless-Event-Mesh Consumption Layer

**Date:** 2026-07-05
**Status:** Approved
**Type:** North-star vision / roadmap (24+ month horizon) — *not* a subsystem design doc. The five chapters are directional, not dated; each becomes its own spec → plan → implementation cycle. The load-bearing claim throughout is honesty: on every individual face Crabka is parity-or-behind versus a specialist incumbent, and the only two defensible moats are the **shared columnar substrate** and the **formal no-acknowledged-loss durability gate**.

## Where Crabka is today

Crabka (v0.3.8, beta, greenfield, no production users) is a broad Apache-Kafka-wire-compatible broker with an unusually complete adjacent stack: KIP-405 tiered storage is GA in-repo with a production S3/GCS/local object-storage remote tier and a JVM-byte-exact, topic-backed remote-log-metadata manager as the default; a decode-free pass-through fetch path with real kernel `sendfile(2)` and Linux kTLS zero-copy-over-TLS already reaches Kafka-wire parity on large-message throughput; a signal-agnostic Parquet-on-object-storage blockstore backs a near-complete Grafana-LGTM+Pyroscope-equivalent observability stack (metrics/PromQL, traces/TraceQL, logs/LogQL, profiles/pprof), each a DataFusion-native, role-selectable binary; and a formal-correctness apparatus — Creusot-verified pure kernels called from production code plus a `stateright` end-to-end durability model — already gates the classic replicated data path. What Crabka does **not** have yet: no 1.0/GA, **no diskless/object-storage-native broker** (zero shared-WAL or stateless-broker code), **no lakehouse/Iceberg surface** (zero Iceberg anywhere in-tree), and **no cross-signal-to-topic query** (no topic-as-`TableProvider`, and even Grafana's built-in signal correlations are unwired). The observability backends are real and strong but are, as a competitive matter, a re-implementation of an existing open-source stack — parity, not yet a moat. The same honesty governs the serverless-event-mesh work in Chapter 4: backing Knative Eventing and speaking CloudEvents over HTTP is interop-and-validation riding on the already-built wire-compatible broker, gRPC/HTTP gateway, and (built, JVM-validated) share-group stack, with a single net-new wedge — share-group backlog autoscaling. This document is the 24-month arc from "broad Kafka parity plus a strong LGTM clone" to "one columnar object-storage substrate presenting four faces, plus a serverless-event-mesh consumption layer that rides them."

## The thesis — one substrate, four faces, plus a consumption layer

The organizing idea is that **broker log data, lakehouse tables, and observability signals are the same thing underneath**: columnar blocks on object storage, coordinated by KRaft, queried by one DataFusion engine, moved by one Rust efficiency core. Build that shared substrate once and the differentiating capabilities stop being separate systems and become *materializations of one substrate*.

- **Chapter 0** carries both the **substrate spine** (the shared `object_store` + Parquet/Arrow + DataFusion layer) and the **efficiency face** (`sendfile` / kTLS / io_uring). It is the fourth face and the foundation for the other three.
- **Chapters 1–3 are the other three faces** — diskless broker, lakehouse topics, unified observability.
- **Chapter 4 is not a face — it is a consumption layer.** It rides the wire-compatible broker, the gateway, and share groups; it stores nothing and adds no substrate. Grading it on the substrate-differentiation axis would (correctly) score it lowest, which is why it sits in a different tier.

```
  consumption ──▶  ┌────────────────────────────────────────────────────┐
      layer        │  Ch.4  Serverless Event Mesh (Knative / CloudEvents)│
                   └────────────────────────────────────────────────────┘
                        ▲ rides wire-compat + gateway + share groups
                   ┌────┴───────────┬───────────────────┬────────────────┐
  three faces  ──▶ │ Ch.1 Diskless  │ Ch.2 Lakehouse    │ Ch.3 Unified   │
                   │ broker (flag.) │ topics (Iceberg)  │ observability  │
                   └────┬───────────┴─────────┬─────────┴───────┬────────┘
                        ▼                      ▼                 ▼
  spine + 4th    ┌──────────────────────────────────────────────────────┐
  (efficiency)──▶│ Ch.0  Shared columnar substrate: object_store +       │
                 │ Parquet/Arrow + DataFusion + KRaft coordination,      │
                 │ plus the efficiency core (sendfile / kTLS / io_uring) │
                 └──────────────────────────────────────────────────────┘
                        ▼
                   object storage (S3 / GCS / R2 / MinIO)
```

Diskless leads because building it *forces the substrate into existence*; lakehouse then falls out of it, observability integration lights up the cross-signal-to-topic query, and the serverless event mesh consumes the whole thing.

## Chapter 0 — The Substrate & Efficiency Core

**Thesis.** Kafka-wire throughput parity is table stakes, and Crabka already has it: byte-exact decode-free fetch, kernel `sendfile(2)`, and Linux kTLS zero-copy-over-TLS answer Kafka's large-message `sendfile` advantage directly. The moat is **not** beating Redpanda on raw MB/s — Redpanda's wins come from a thread-per-core Seastar/io_uring C++ architecture Crabka has not built and which is currently blocked by policy (`unsafe_code = "forbid"`), and AutoMQ competes on diskless cost/elasticity rather than `sendfile` throughput at all. The defensible bet is the **shared columnar substrate**: one `object_store` + Parquet/Arrow + DataFusion layer that broker log data, lakehouse tables, and observability signals all ride, so that WarpStream/Freight/Tableflow-class capabilities fall out of parts already in-tree instead of being bolted on as separate systems. Chapter 0 is the spine — it makes the substrate literally shared and hardens the efficiency core to Kafka parity — and it confronts head-on the raw-vs-columnar dual-representation question that is the single biggest threat to the storage-efficiency story.

**What we stand on today**
- Decode-free pass-through fetch — header-only batch scan forwards verbatim on-disk wire bytes with no decode/re-encode round-trip: `crates/log/src/log.rs` (`read_raw`, `RawRead`, `VerbatimBatch`), `crates/protocol/src/records/payload.rs` (`RecordsPayload::Raw`), design in `docs/superpowers/specs/2026-05-28-crabka-fetch-decode-free-passthrough-design.md`.
- Kernel `sendfile(2)` zero-copy-to-socket for large fetches, gated at `SENDFILE_MIN_BYTES = 32 KiB`, with an `Arc<File>` `FileRegion` that pins the inode against retention truncation: `crates/broker/src/network/fetch_writer.rs` (`sendfile_region`, `drain_file_region`), `crates/log/src/segment.rs` (`read_raw_desc`, `FileRegion`), decision at `crates/broker/src/handlers/fetch.rs`.
- **Linux kTLS zero-copy sendfile-over-TLS is already shipped and wired end-to-end** — `ktls = "6"` is a direct workspace dependency (`Cargo.toml`, `crates/broker/Cargo.toml`); TLS connections terminate through `ktls::CorkStream` + `ktls::config_ktls_server` in `crates/broker/src/network/dispatch.rs`; `impl SendfileSink for ktls::KtlsStream<TcpStream>` in `crates/broker/src/network/fetch_writer.rs` returns the raw socket so real `sendfile(2)` regions are emitted and the kernel encrypts them into TLS records; `serve_connection_stream` is generic over `SendfileSink`. `ktls_probe.rs` is only the one-shot startup capability check, not the extent of support.
- KIP-405 tiered-storage SPI and reference impls that write sealed segments to S3/GCS/local object storage via the Apache `object_store` crate: `crates/remote-storage/src/{s3.rs,gcs.rs,local.rs,storage_manager.rs}`.
- A signal-agnostic columnar block store — tenant-scoped time-bounded Parquet on object storage, a label/series index that prunes to candidate blocks before any scan, DataFusion for row-group pruning/pushdown: `crates/blockstore/src/{lib.rs,store.rs,index.rs,block.rs,writer.rs,reader.rs}`.
- An mmap read-path benchmark harness that isolates the exact byte-fetch mmap would replace and documents that `unsafe_code = "forbid"` currently makes `memmap2` uncallable from any workspace crate: `crates/log-iobench/` (`benches/mmap_read.rs`, `README.md`), workspace lint at `Cargo.toml`.

**The arc**
1. **Name and measure the efficiency core.** Promote the already-shipped decode-free + `sendfile` + kTLS fetch path into an explicit "efficiency core" subsystem with a throughput benchmark vs a `cp-kafka` image on large messages via `crates/bench-driver`. The genuine remaining gaps — verified absent — are **io_uring**, **production mmap** (blocked by `unsafe_code = "forbid"`; `memmap2` lives only in `log-iobench`), and a **reusable buffer pool** (jemalloc is opt-in for heap profiling only). kTLS is done and drops off the to-build list.
2. **Choose and prototype the runtime/buffer strategy.** The broker is plain tokio `rt-multi-thread`; `io-uring` in `Cargo.lock` is only an incidental transitive dependency (pulled in via the query-engine stack, under `turso`/`turso_core`), not a runtime Crabka has adopted. Prototype a thread-per-core / io_uring option (`monoio` or `tokio-uring`) behind a runtime seam for the produce/fetch hot loop, plus a buffer arena for the response buffer that pass-through still copies once. This requires resolving the `unsafe` policy — a sanctioned narrow `unsafe` seam or a vetted external crate — a decision not yet made. Gate adoption on `bench-driver` numbers, not faith. Matching Redpanda's thread-per-core throughput is an explicit **stretch goal**, contingent on that policy decision.
3. **Unify the two object-store stacks into one substrate crate.** Today `crabka-log`/`remote-storage` write raw verbatim Kafka segment bytes while `crabka-blockstore` writes Parquet+index; they share only the `object_store` dependency, not a substrate. Extract a shared substrate crate owning the `object_store` handle, path/prefix layout, block/segment lifecycle, and index conventions, consumed by **both** the KIP-405 remote tier and blockstore.
4. **Make broker log data columnar-capable on the shared substrate.** Give the substrate a mode where broker segment data materializes as Parquet+series-index blocks, so a topic's bytes are simultaneously Kafka-fetchable (verbatim, `sendfile`) and DataFusion-queryable — the precondition for Chapters 2 and 3.

**The dual-representation bet (stated, not buried).** Verbatim Kafka bytes are row-oriented and compressed; Iceberg/query data files are columnar Parquet. The same bytes cannot be both a byte-exact fetch payload and a Parquet data file. The design bet is that this is **not** 2× steady-state storage: **raw verbatim bytes are the hot-tail cache serving the low-latency `sendfile` fetch path, and Parquet is the authoritative cold projection on object storage**, with the raw tail aged out under retention. Whether the crossover economics hold across real workloads — versus degrading into a genuine double-write that erodes the WarpStream/AutoMQ storage-cost advantage — is an explicit open question this chapter must answer with measurement, not assert away.

**Success signal.** A single `crates/bench-driver` run against a `cp-kafka` image shows Crabka matching or beating Kafka on large-message fetch throughput on **both** a plaintext and a TLS listener (the `sendfile`/kTLS core), while the same segment's bytes are queryable through DataFusion via the shared substrate crate that both the KIP-405 remote tier and `crabka-blockstore` now import — with no second copy of the object-store read path in the codebase.

**Key risk.** "One substrate" is today a slogan, not a fact — the two stacks are genuinely disjoint. Forcing broker data to be simultaneously verbatim-fetchable and columnar-queryable risks a real double-write that erodes the storage-efficiency advantage. Compounding this, the core's biggest throughput wins (io_uring, production mmap, in-place zero-copy) all require `unsafe`, which the workspace-wide `unsafe_code = "forbid"` prohibits, so raw-throughput parity with Redpanda cannot be reached without a policy decision that has not been made.

## Chapter 1 — Diskless / Object-Storage-Native Broker (flagship)

**Thesis.** The diskless *architecture* — a low-latency shared WAL absorbing acks in single-digit milliseconds, batched flushes landing the durable copy in object storage, KRaft assigning offsets so brokers are stateless and interchangeable — is deliberately the WarpStream / Confluent Freight / AutoMQ / KIP-1150 "Inkless" model, and as pure architecture it is **parity catch-up, not novelty**: Crabka would arrive years after WarpStream (GA, acquired by Confluent) and AutoMQ (GA). Crabka's differentiated wedge is twofold and is the headline, not the footnote: **(1)** it reaches diskless *from* an already-shipping KIP-405 stack (object-store RSM, JVM-byte-exact topic-backed metadata, remote-read positioning) rather than from zero, and **(2)** it is **the only diskless broker whose no-acknowledged-loss property is machine-checked before GA** — the same Creusot kernels and `stateright` model that today gate the classic path are extended to prove diskless never loses acknowledged data, as a hard shipping gate. The inviolable constraint: clients never learn the broker is diskless — every request/response stays Kafka-wire-exact.

**What we stand on today**
- Full KIP-405 tiered storage, GA in-repo: SPI + metadata state machines, copy path, local/remote retention split with local-log-start-offset, remote read positioning, remote retention + partition delete: `crates/remote-storage/src/{metadata.rs,cache.rs,storage_manager.rs,local.rs,s3.rs}`, `docs/superpowers/specs/2026-05-25-crabka-tiered-storage-roadmap-design.md`.
- Production object-storage `RemoteStorageManager` on the Apache `object_store` crate (S3, MinIO, R2, GCS), same object-key layout as the filesystem RSM: `crates/remote-storage/src/s3.rs`.
- Durable, multi-broker-safe remote metadata: `TopicBasedRemoteLogMetadataManager` backed by `__remote_log_metadata`, **the default**, fail-closed bootstrap via `SwappableRlmm`/`NotReadyRlmm`, records byte-exact with the JVM `RemoteLogMetadataSerde`: `crates/remote-storage-topic/src/lib.rs`, golden test `crates/remote-storage-topic/tests/jvm_serde_golden.rs`.
- A sans-IO KRaft consensus core plus the async Raft engine and KIP-853 voter model — the coordination layer diskless uses to assign offsets and track segment ownership: `crates/kraft-core/src/core.rs` (`QuorumStateMachine`, `LogView`), `crates/raft/src/` (`Controller`, `kraft/`), `crates/voters/src/lib.rs`, `crates/metadata/src/image.rs`.
- The durability-correctness apparatus that carries the gate: Creusot-verified pure kernels called directly by production code (`crates/verified/src/{consensus.rs,compaction.rs,log_index.rs}`, `docs/verification.md`) plus a compositional `stateright` model proving an `acks=all` record is never lost across clean leader changes (`crates/broker/src/data_path_model.rs`, with `crates/broker/src/{replica_state.rs,isr_maintenance.rs,partition_writer.rs}`).

**The arc** *(the entire chapter is 0% built today — verified: no diskless or shared-WAL code in broker or log; KIP-1150 is "long-term in scope" per `docs/KIP_MATRIX.md`. This is a bet, not a lead.)*
1. **M1 — Shared low-latency WAL resolving the PUT-latency-vs-ack tension.** Acks are today bound to the local segmented log (`crates/log`) and ISR replication (`crates/broker/src/{isr_maintenance.rs,partition_writer.rs}`); object storage holds only cold sealed segments. Object-storage PUT latency (tens–hundreds of ms) is incompatible with Kafka's single-digit-ms ack expectation. M1 introduces a quorum-durable shared WAL that acks in ms and batches for later flush, built on the existing sans-IO KRaft engine (`crates/kraft-core`, `crates/raft`) rather than a new consensus layer.
2. **M2 — Batched flush + KRaft-coordinated offset assignment, statelessly.** Drain the WAL into object-storage objects reusing the `object_store`-backed RSM (`crates/remote-storage/src/s3.rs`) and the JVM-byte-exact segment index (`crates/remote-storage-topic`). Offsets are assigned via KRaft (`crates/metadata`, `crates/raft`) so any broker can accept a write and any broker can serve a read. Fetch serves from object storage through existing remote-read positioning (`crates/broker/src/remote_reader.rs`) with the WAL as the hot tail — no local replicated log required.
3. **M3 — Durability-correctness gate (SHIPPING GATE).** The ack boundary moves from local-log HWM to WAL-commit + object-flush, so the proof obligations move with it. Extend `crates/verified` Creusot kernels and add a `stateright` model alongside `crates/broker/src/data_path_model.rs` asserting: every WAL-acked record is eventually durable in object storage; a flush crash mid-PUT never acks-then-loses; offset assignment is gap-free and monotonic under concurrent brokers and KRaft leader changes; no acknowledged record is lost across broker death, WAL-node loss within quorum, or PUT failure. Jepsen-style black-box tests assert the same against a running cluster. **Diskless does not ship until green.**
4. **M4 — Diskless topics GA behind the wire-compat and cost invariants.** Land diskless as a per-topic mode selectable via topic config and operator CRD (`crates/operator`), coexisting with classic-replicated and tiered topics on one cluster. Prove the differentiators empirically: near-zero inter-AZ transfer bytes vs a classic `acks=all` topic, seconds-scale broker add/remove, and unchanged JVM-tool behavior — `kafka-reassign-partitions` on a diskless topic becomes a metadata-only no-op. Ships only after M3 passes.

**Success signal.** A three-broker cluster runs a diskless topic where an `acks=all` produce is acknowledged in single-digit ms (WAL-bound, not PUT-bound); killing the broker that accepted the write, or forcing a PUT failure, loses zero acknowledged records; a JVM `kafka-console-consumer` replays byte-for-byte with no knowledge the broker holds no local log; inter-AZ transfer bytes are effectively zero vs a classic control topic; a freshly added broker serves the partition within seconds — all gated by a green Creusot + `stateright` + Jepsen suite that mechanically proves no acknowledged record is ever lost.

**Key risk.** The WAL is the entire bet and the entire risk: it must simultaneously hit single-digit-ms acks, be quorum-durable within the failure budget, and hand off to object storage without ever acking-then-losing across the flush boundary — while the offset sequencer stays gap-free and monotonic under concurrent stateless brokers and KRaft leader turnover. If that WAL→flush→offset durability proof cannot be closed in Creusot/`stateright`/Jepsen, diskless cannot ship: a diskless broker that silently loses an acknowledged write behind a byte-identical Kafka wire is strictly worse than shipping nothing, precisely because clients trust the ack *because* they cannot see the broker is diskless.

## Chapter 2 — Lakehouse-Native Topics: Your Topics Become Iceberg Tables

**Thesis.** Once Chapter 1 makes topic data live as columnar files on object storage, the lakehouse face is a materialization detail, not a second system. The honest, defensible wedge is **colocation + in-process SQL**, not a "same bytes / zero re-encode" claim (which is false: Kafka's on-disk batch format is row-oriented and compressed, Iceberg data files are columnar Parquet — the materializer *must* decode and re-encode, exactly like Redpanda Iceberg Topics and Confluent Tableflow do). Crabka's differentiation is that **the Parquet projection is colocated in the same object-store bucket and query engine** rather than shipped to a separate lakehouse system, and that **in-process DataFusion plus a future Flight-SQL surface give Crabka a query face WarpStream and Freight lack entirely**. Crabka already owns a production DataFusion+Parquet+`object_store` engine (`crates/blockstore`) and a Confluent-compatible Schema Registry with real evolution checks (`crates/schema-registry`), so the *plumbing* has a genuine head start — but the *correctness core* does not fall out cheaply, and this chapter says so plainly.

**What we stand on today**
- A mature signal-agnostic columnar blockstore — time-bounded Parquet on `object_store`, a label/series index pruning before scan, DataFusion pushdown, `BlockWriter`/reader/`BlockStore`/`ScanTableRequest`: `crates/blockstore/src/{lib.rs,store.rs,writer.rs,reader.rs,block_index.rs}`. It currently indexes observability signals, not topic segments.
- The KIP-405 SPI: a `RemoteStorageManager` copying `LogSegmentData` (opaque Kafka `.log` bytes + indexes) to object storage, with a topic-backed metadata manager tracking per-segment lifecycle: `crates/remote-storage/src/storage_manager.rs`, `crates/remote-storage-topic/src/lib.rs` — the exact seam a topic→Parquet materializer taps.
- A Confluent-compatible Schema Registry with Avro/Protobuf/JSON and the full `CompatibilityLevel` matrix (Backward/Forward/Full + Transitive), backed by `_schemas`: `crates/schema-registry/src/format/`, `crates/schema-registry/src/compat/mod.rs`.
- A row↔columnar bridge already prototyped: `RowBridge` (`rows_to_frame`/`frame_to_rows`) and a `RowCodec` deserializing Kafka `(key,value)` records through registry serdes into Arrow/Polars frames with reserved `__key`/`__offset`/`__timestamp`/`__partition` columns: `crates/client-streams/src/columnar/topology/codec.rs`, `row_bridge.rs`, `serde/arrow.rs`.
- Confluent wire framing decode (`magic|schema_id|body`, incl. Protobuf message-index) and a Connect runtime with a working Postgres logical-decoding CDC-in path producing typed `EntityDifference` envelopes: `crates/schema-serde/src/wire.rs`, `crates/connect/src/sink.rs`, `crates/connect-postgres/src/model.rs`.
- A Connect-RPC/HTTP gateway over topics that decodes records schema-aware (`DecodedConsumerRecord` carries schema + JSON projection): `crates/grpc-gateway/src/lib.rs`, `consume.rs` — the natural host for a future SQL/Flight-SQL endpoint.

**The arc** *(zero Iceberg exists anywhere in-tree today — no `iceberg-rust` dependency, no manifests, no catalog; this chapter is 100% unbuilt and cannot lean on "we already do it.")*
1. **Segments land as Parquet (the topic→table materializer).** Hook the `RemoteStorageManager` copy path (`crates/remote-storage`): on each sealed segment, decode records through the registry serde (`crabka-schema-serde` wire framing) using `RowBridge`/`RowCodec` lifted from `crates/client-streams/columnar`, and write Parquet via `crabka-blockstore`'s `BlockWriter` with the reserved `__key`/`__offset`/`__timestamp`/`__partition` columns. The Kafka `.log` bytes stay authoritative for consumers; **Parquet is a derived, colocated projection** — a real re-encode, colocated, not a second system. This is the single hardest new piece.
2. **Maintain an Iceberg table + manifests over those Parquet files.** Add an Iceberg manifest/metadata writer registering each materialized Parquet file as a data file in a per-topic table, deriving the schema from the topic's registered subject in `crabka-schema-registry`. Map the registry's `CompatibilityLevel` transitions (`crates/schema-registry/src/compat`) onto Iceberg schema-evolution ops (add/rename/widen column, new schema-id). Snapshots advance as segments tier; compaction/expire-snapshots reuse blockstore's block-compaction machinery.
3. **SQL over topics in-process via the already-present DataFusion engine.** Register the per-topic Iceberg/Parquet table as a DataFusion `TableProvider`, answer `SELECT`s in-process, expose them through `crabka-grpc-gateway`, and add an Arrow Flight SQL server (not yet a dependency) so BI/notebook clients connect natively — a query face WarpStream/Freight lack entirely.
4. **External engines read topics as Iceberg tables with zero ETL.** Publish the table into a standard catalog (REST catalog endpoint on the gateway, or Glue/Nessie adapters) so Spark, Trino, and DuckDB open Crabka topics as ordinary Iceberg tables against the same bucket. **No connector, no Flink job, no separate lakehouse destination** — the topic's tiered Parquet *is* the table's data files (a colocated derived copy, not a re-shipped one). Close the loop with the existing `crates/connect` + `connect-postgres` CDC-in path so a Postgres table streams into a topic that is instantly an Iceberg table.

**Altitude note — the hard half does not fall out cheaply.** The schema-registry, DataFusion, and `RowBridge` reuse is a genuine head start on the *plumbing*. It is **not** a head start on the *correctness core*: exactly-once, transaction-boundary-aware materialization, and keeping Iceberg table state exactly consistent with Kafka topic state across retention, compaction, aborted transactions, tombstones/compacted topics, and mid-stream schema evolution is exactly where Tableflow-class systems spend most of their engineering, and there is zero code for it in-tree. A row visible to Trino that a Kafka consumer never saw (or vice versa) silently breaks the whole promise.

**Success signal.** Produce Avro/Protobuf records to a topic; a Kafka consumer reads them byte-exact while, with zero connector or ETL job, `spark.read.format("iceberg").load("crabka.<topic>")` (and equally Trino and DuckDB) returns the same rows against the same bucket — and a `SELECT ... GROUP BY` answered in-process by Crabka's own DataFusion/Flight-SQL endpoint matches the external engines. Then evolve the subject's schema (a Backward-compatible field add) and watch the Iceberg table schema evolve without rewriting a single existing Parquet file.

**Key risk.** Two coupled risks. **(1) Structural dependency:** blockstore (observability-only) and remote-storage (opaque Kafka `.log` bytes) are two disconnected halves today; the chapter's entire value depends on Chapter 1 fusing them so topic segments materialize as Parquet on the shared substrate. If that fusion slips, the materializer has nothing columnar to write into. **(2) Consistency correctness:** exactly-once, transaction/tombstone/retention/schema-evolution-consistent materialization is the genuinely hard, unbuilt work — and there is no Iceberg code in-tree to build on.

## Chapter 3 — Unified Streaming + Observability

**Thesis.** The four LGTM+Pyroscope-equivalent backends being real and DataFusion-native over one signal-agnostic Parquet blockstore is a strong engineering fact — but as a competitive matter it is a **re-implementation of an existing open-source stack, i.e. parity, not a moat**. The one thing no incumbent can reach is the unifying move: **because observability signals AND Kafka topics can share one `object_store` bucket and one DataFusion engine, correlate a trace or a log line with the exact records on the topic that produced it, in a single query.** Grafana ships each signal as its own service (Mimir/Loki/Tempo/Pyroscope) with its own storage; the streaming vendors (WarpStream, Redpanda, AutoMQ, Bufstream) ship a broker and stop. Crabka's wedge is the cross-signal-to-topic join. This chapter must state its top-line dependency plainly: that payoff is **transitively gated on Chapter 2's lakehouse substrate** (topics-as-`TableProvider`) landing first. If Chapter 2 slips, Chapter 3 delivers only a well-packaged LGTM-equivalent — strong, but parity, and matchable by incumbents.

**What we stand on today**
- Signal-agnostic columnar blockstore already carrying the cross-signal join keys: `crates/blockstore/src/profile_schema.rs` (`PCOL_TRACE_ID`/`PCOL_SPAN_ID`, plus a `cross_signal_join_keys_are_nullable` test), `crates/blockstore/src/span_schema.rs` (`SCOL_TRACE_ID`).
- Four complete backends, each a role-selectable binary (distributor/compactor/block-builder/querier) whose WAL is Crabka Kafka topics: `crates/metrics` (`WAL_TOPIC __crabka_metrics_wal` in `src/wal.rs`, Prom/Mimir remote-write + OTLP), `crates/traces` (Tempo: OTLP/Jaeger/Zipkin, TraceQL), `crates/observability` (Loki push + LogQL), `crates/profiles` (Pyroscope push + pprof).
- Four DataFusion-native query engines: `crates/promql/src/engine.rs` and `crates/traceql/src/engine.rs` lower to DataFusion `LogicalPlan`/`SessionContext`; `crates/logql` and `crates/pprof` run over the shared blockstore.
- A cross-signal generator already in-tree: the traces metrics-generator role derives RED span-metrics and a service graph from the trace WAL and remote-writes them into the metrics backend: `crates/traces/src/metricsgen/{mod.rs,spanmetrics.rs,servicegraph.rs,remotewrite.rs}`.
- Self-observability: `crates/telemetry/src/lib.rs` (`OtlpConfig`, `init`), `crates/telemetry/src/profiling.rs` (`/debug/pprof/*`), `crates/telemetry/src/propagation.rs` (W3C `traceparent` over Kafka record headers). The broker wires OTLP via `crate::telemetry::OtlpConfig::from_env(...)` at `crates/broker/src/broker.rs:2859`, exposes Prometheus `/metrics` on `:9404`, and serves in-process pprof CPU/heap.
- The "Crabka observes Crabka" demo is built and ahead of its design doc: a ~20-container `docker compose` stack where one broker is triple-duty (business event bus + WAL for all four backends + self-observed subject), Alloy collecting all four signals, a real `crabka-client-streams` orders pipeline on the broker, and Grafana provisioned with **4 datasources + 10 dashboards** (`crabka-broker`, `crabka-demo`, `crabka-overview`, `crabka-runtime`, `crabka-rustfs`, `crabka-self`, `crabka-svc-{logs,metrics,traces,profiles}`): `demo/observability/docker-compose.yml`, `demo/observability/README.md`, `demo/observability/grafana/provisioning/`, `crates/observability-demo-app/src/main.rs`.

**The arc**
1. **Crabka observes Crabka — harden the demo into a supported deployment.** The end-to-end self-observability stack already exists (mostly built, ahead of its design doc). It currently pulls a prebuilt GHCR image and is explicitly non-CI-gated / manual-smoke-only. Productize: a supported, versioned, documented deployment.
2. **Ship the LGTM+P-equivalent as a supported product alongside the broker.** The four backends and four query engines are strong and role-selectable over the shared blockstore. Productization: a first-class packaged deployment (the demo proves compose viability), tenancy/limits/retention hardening (crates already have `limits/` + overrides + compactor retention), and closing the `crabka-logs` entrypoint gap (logs still run via the `crabka-observability` library binary with `--target`). **This is parity with Grafana's stack, and the doc says so — it is table stakes for the wedge, not the wedge.**
3. **The unifying move — cross-signal correlation, then query across signals and the topics themselves.** Two layers. **(a)** Wire the Grafana correlations that are trivially absent today: `demo/observability/grafana/provisioning/datasources/crabka.yaml` wires no `tracesToLogs`/`tracesToProfiles`/`derivedFields`/`exemplars`, even though the substrate already carries the join keys (`PCOL_TRACE_ID`/`SCOL_TRACE_ID`). Wire Tempo↔Loki↔Pyroscope↔Prometheus so a trace jumps to its logs, its flamegraph, and its RED metrics. **(b)** The move nobody else has: expose a single query surface that joins a trace/log against the exact events on the topic that produced it. **This does not exist yet** — there is no topic-as-`TableProvider` anywhere (confirmed absent in broker/log/remote-storage/remote-storage-topic; `TableProvider` exists only in blockstore/promql/traceql for observability signals), and each querier is siloed. It depends on Chapter 2's lakehouse substrate landing; this chapter contributes the signal-side join keys, a federating query gateway, and the correlation UX.

**Success signal.** A single `docker compose up` stands up one broker serving both business topics and the WAL for all four telemetry backends; in Grafana an operator opens a slow request's trace, clicks straight through to that request's logs and its CPU/heap flamegraph via wired Tempo→Loki→Pyroscope correlations, then runs **one query that joins the trace against the exact records on the Kafka topic that produced it** — all backed by one object-store bucket and one DataFusion engine, with no external Mimir/Loki/Tempo/Pyroscope processes running.

**Key risk (top-line, not a footnote).** The headline differentiator — query across signals AND the topics themselves — is the one thing not built, and it is **transitively gated on Chapter 2's unbuilt lakehouse substrate**. There is no topic-as-`TableProvider` anywhere, no federating surface across the four siloed queriers, and even the trivial Grafana correlation win is unwired. If Chapter 2 slips, this chapter collapses to a well-packaged LGTM-equivalent — feature parity with an existing open-source stack, easily matched by incumbents, and precisely the "master of none" trap. The four real backends are strong, but they are a re-implementation, not a moat.

## Chapter 4 — Serverless Event Mesh (Knative / CloudEvents)

**Thesis.** Backing Knative Eventing is Crabka's *cheapest* new face and, on its own, its *least differentiated*: because Crabka is Kafka-wire-exact, the upstream `eventing-kafka-broker` (`KafkaBroker`/`KafkaChannel`/`KafkaSource`/`KafkaSink`) largely runs against Crabka **for free**, so this facet is an interop-and-validation effort in the spirit of Chapter 3 — table stakes already crossed by Strimzi and Redpanda, not novel engineering. The actual wedge is narrow and must be named precisely: **share groups (KIP-932) as the competing-consumer / queue model for serverless functions, with broker-computed backlog (`DescribeShareGroupOffsets`, HWM−SPSO) driving event-driven autoscaling — a primitive that is built and JVM-validated in Crabka today and has no equivalent in any KEDA scaler or in the Redpanda/Strimzi Knative stacks.** Two lesser threads reinforce it as connective tissue, not standalone moats: a **CloudEvents-native gateway** (produce/consume CloudEvents over HTTP with no Kafka client) whose only defensible value is combinatorial — the *same* substrate is simultaneously a Kafka broker, a CloudEvents endpoint, and the observability store; and a **diskless ↔ scale-to-zero synergy** that is entirely *future-gated on Chapter 1* (0% built) and must be stated as a promise, not a present capability.

**What we stand on today**
- **Share groups (KIP-932) are implemented and JVM-validated in-tree — this is the wedge, and it is built, not roadmap.** `DescribeShareGroupOffsets` (api key 90) serves per-share-partition backlog computed as `(hwm.0 - start_offset).max(0)` (HWM−SPSO) at `crates/broker/src/handlers/describe_share_group_offsets.rs:230`; the full share stack is real — a 767-line acquire-pass/long-poll `crates/broker/src/handlers/share_fetch.rs` (zero `todo!`/`unimplemented!`), the per-group coordinator/persister at `crates/broker/src/share_coordinator/` (10 modules) and partition-leader state at `crates/broker/src/share_partition/` (5 modules), all dispatched at `crates/broker/src/handlers/registry.rs:634-636`, and differential JVM tests at `crates/broker/tests/{jvm_share_groups.rs,share_consume.rs,share_admin_offsets.rs}` + `crates/integration-tests/tests/consumer_share_consumer.rs`. KIP-932/1206/1222/**1226** (share-group lag) are tracked in `docs/KIP_MATRIX.md`. (The 2026-05-30 spec header at `docs/superpowers/specs/2026-05-30-crabka-kip-932-share-groups-design.md` still says "Slice A only / the broker does nothing" — that language is **stale**; the full A–F implementation and that spec landed in the same commit.)
- **Every KEDA-scaler-critical admin API is a real broker handler**, so KEDA's stock `kafka` scaler reads consumer-group lag (`ListOffsets` end − `OffsetFetch` committed) against Crabka with **no broker change**: `crates/broker/src/handlers/{list_offsets.rs,offset_fetch.rs,list_groups.rs,describe_groups.rs,consumer_group_describe.rs}`.
- **The broker surface `eventing-kafka-broker` depends on is entirely present** — transactional/EOS producer path (`crates/broker/src/txn/` + `init_producer_id.rs`, KIP-98/447/890/939 per `docs/KIP_MATRIX.md`, 2PC proven by a `stateright` model), consumer groups classic + KIP-848 next-gen (`crates/broker/src/coordinator/unified/`), topic/config/ACL admin (`create_topics.rs`, `create_partitions.rs`, `describe_configs.rs`, `metadata.rs`), and **record headers end-to-end** — the transport that CloudEvents binary mode rides: `RecordHeader` in `crates/protocol/src/records/{owned.rs,borrowed.rs}`, producer `Header` in `crates/client-producer/src/record.rs`, `ConsumerRecord.headers` in `crates/client-consumer/src/consumer.rs:117`.
- **The gateway is a stateless, Deployment-shaped, HTTP-fronted Kafka client** — the natural CloudEvents host and a Knative-Serving candidate: it already reconciles to a `Deployment` + `ClusterIP` Service via a `KafkaGrpcGateway` CRD (`crates/operator/src/controller/grpc_gateway.rs`, `DEFAULT_REPLICAS`; CRD at `crates/operator/src/crd/grpc_gateway.rs`), is config-only `bootstrap:` (`config.rs`), and already serves HTTP produce ingress at `POST /v1/produce/{topic}` and `POST /v1/webhooks/{name}` (`webhook.rs`). The transport-agnostic core seam is present: `GatewayRecord.headers: Vec<(String, Bytes)>` (`crates/grpc-gateway/src/types.rs:23`), a `RecordCodec` seam, and Confluent structured framing (`magic|schema_id|body`) at `crates/schema-serde/src/wire.rs`.
- **Absent, and honestly so — the entire CloudEvents/Knative binding is net-new.** A tree-wide grep for `cloudevents|knative|eventing-kafka|keda|scale-to-zero` returns nothing. Concretely, the gateway binds no CloudEvents semantics: the HTTP inbound handlers hardcode `headers: vec![]` (`webhook.rs:198,249`); the outbound egress emits a **proprietary `X-Crabka-*` JSON envelope** and **drops record headers** even though `ConsumerRecord` carries them — `render_envelope` at `outbound.rs:285`, whose own doc comment ("The envelope omits record headers") and a stale sibling comment claiming "ConsumerRecord exposes none" both need fixing when binary mode lands; and `DecodedConsumerRecord` (`consume.rs:16`) has **no `headers` field at all**, so egress binary mode has no source today.
- **The diskless elasticity this face wants to pair with is 0% built.** Brokers today are pets: `KafkaNodePool` reconciles to a `StatefulSet` + `PersistentVolumeClaim` with storage-immutability guards (`crates/operator/src/controller/kafka_node_pool.rs`) — exactly what cannot scale in seconds. The seconds-scale broker tier is a Chapter-1 promise, not a present capability.

**The arc** *(net-new work is Facet 2's CloudEvents binding and Facet 3's share-group→KEDA bridge; Facet 1 is a qualification gate, and Knative-Serving packaging is a deployment footnote — see below. The diskless half of Facet 3 is gated on Chapter 1.)*
1. **Facet 1 — Pass `eventing-kafka-broker` conformance as a QUALIFICATION GATE, not a feature.** Stand the upstream reconcilers + data-plane dispatcher/receiver against a Crabka cluster and run its e2e/conformance suite inside the existing JVM-acceptance harness that already drives `cp-kafka` admin tools. This exercises only surface already built (topic/config admin, transactional dispatch, offset commit, header round-trip). **Budget it as CI/interop scaffolding measured in test wiring; passing confers zero differentiation because Strimzi and Redpanda already pass it, and any failure is a wire-compat *bug* against the existing broker, not Chapter-4 scope.** Crabka must clear this line to *credibly claim the other facets* — nothing more.
2. **Facet 3 (the sharpest wedge) — Bridge share-group backlog into event-driven autoscaling. NET-NEW.** The competing-consumer backlog primitive already exists (`DescribeShareGroupOffsets`, HWM−SPSO, built + JVM-validated); the unbuilt piece is the scaler bridge, because **no upstream KEDA share-group scaler exists**. Ship a KEDA external/metrics scaler (or a Prometheus-gauge bridge over the existing `/metrics`) fed by a `DescribeShareGroupOffsets` poller, so KEDA scales serverless competing-consumers on share-group backlog where a consumer-group-only scaler structurally cannot. The bridge must query the leader per share-partition (or aggregate fleet-wide) to avoid the best-effort `-1` lag — see Key Risk.
3. **Facet 3 (validation half) — Confirm stock KEDA consumer-group scaling as an interop FACT.** A KEDA `kafka`-scaler `ScaledObject` against Crabka, asserting it reads lag through the existing `ListOffsets`/`OffsetFetch`/`DescribeGroups` handlers. This is a conformance test, not broker code: "KEDA already scales on any Kafka; we prove Crabka is any-Kafka." No differentiation on its own.
4. **Facet 3 (diskless synergy) — FUTURE, gated on Chapter 1.** Once diskless stateless brokers exist (0% today), pair backlog-driven scale-to-zero of *consumers* with seconds-scale add/remove of *brokers* (metadata-only, near-zero local state) — the "diskless elasticity ↔ event-driven scaling" pairing that a classic-`StatefulSet`+PVC broker categorically cannot do. State this as a promise riding on the flagship, not a present capability.
5. **Facet 2 — CloudEvents Kafka Protocol Binding as a gateway codec. NET-NEW.** Binary mode: map `ce_*` record headers + `content-type` ↔ CloudEvent attributes over the existing `RecordHeader` plumbing. Structured mode: whole CloudEvent as the record value, reusing the Confluent framing at `schema-serde/src/wire.rs`. Both plug into the `RecordCodec`/`GatewayRecord.headers` seam.
6. **Facet 2 — CloudEvents HTTP ingress/egress so a caller needs no Kafka client. NET-NEW.** Teach `webhook.rs` inbound to read `ce_*`/structured bodies into `GatewayRecord.headers`+value (today `headers: vec![]`); replace/extend the proprietary `outbound.rs` envelope with a real CloudEvents HTTP binding (binary + structured), rendering the record headers it currently drops and fixing the stale "exposes none" comment; add a `headers` field to `DecodedConsumerRecord` so egress binary mode has a source. Pitch this only combinatorially (one substrate = broker + CloudEvents endpoint + observability store), never as a standalone moat.

**Success signal.** Three concrete, demoable checkpoints. **(1) Qualification:** the upstream `KafkaSource`→`KafkaSink` round-trip and `eventing-kafka-broker` conformance suite go green against Crabka with no broker patches. **(2) CloudEvents-native:** a CloudEvent produced over plain HTTP to the gateway (binary mode, `ce_*` headers) is consumed by a stock JVM Kafka client **byte-exact**, and the reverse — a Kafka-produced record egresses as a spec-conformant CloudEvent over HTTP with headers intact. **(3) The wedge:** a KEDA `ScaledObject` scales a serverless function to **zero** on drained share-group backlog and back up on a `DescribeShareGroupOffsets`-observed spike — competing-consumer autoscaling on a signal no other Kafka-compatible Knative stack exposes.

**Key risk.** The honest risk is twofold. **Strategically**, three of the four facets are parity: backing Knative Eventing (Facet 1) is table stakes already shipped by Strimzi/Redpanda — worse, it consumes budget to reach a starting line others crossed, and any nit found reads as a *regression*, not a feature; the CloudEvents-over-HTTP convenience (Facet 2) is a checkbox NATS/JetStream and Google Pub/Sub+Eventarc already tick; running stateless services on Knative Serving is what Knative is *for*. Presenting any of these as novel would repeat the "master of none" trap the roadmap's honesty spine exists to avoid. The single defensible wedge — share-group backlog autoscaling — is real and built, but its moat is *timing/integration* (being first to wire share-group lag into event-driven scaling on a wire-compatible broker), not an inventive primitive: share groups are a Kafka KIP, not Crabka-proprietary. **Technically**, that wedge's own signal is best-effort: `DescribeShareGroupOffsets` returns `lag = -1` when the data partition isn't materialized on the queried broker (`describe_share_group_offsets.rs:232,236`). A naive KEDA bridge that reads `-1` as "no backlog" will **scale a backlogged function to zero** and starve it. Building the bridge to query the leader per share-partition or aggregate fleet-wide — so `-1` gaps never cause a false scale-down — *is* the actual net-new engineering for the sharpest wedge: the primitive exists; the correct fleet-wide aggregation and scaler integration do not.

**Altitude note — what does NOT fall out cheaply.** This chapter is Crabka's lowest-altitude, least-differentiated face, and the doc must frame it that way. Facet 1 is CI/interop wiring, not a subsystem; Facet 2 is a bounded codec + HTTP-binding effort on a gateway that already has the right seams (`GatewayRecord.headers`, `RecordCodec`, Confluent framing) — real work, but plumbing, not invention; Facet 4 (services on Knative Serving) is a manifest, not Rust. None is a bet in the Chapter-1 sense. The two things that genuinely do *not* fall out cheaply are (a) the **share-group→KEDA bridge with correct fleet-wide backlog aggregation** (the `-1`-avoidance is the real engineering), and (b) the **diskless-broker seconds-scale elasticity** the scale-to-zero synergy leans on, which is **entirely gated on Chapter 1 (0% built)**. Chapter 4 earns its place only as connective tissue for the one-platform story (broker + event-mesh + observability on one substrate) and as the consumption-side expression of diskless elasticity — never as a standalone moat.

## Cross-cutting invariants

These hold across all four chapters and are non-negotiable.

- **Kafka wire-compatibility is inviolable.** Byte-exact request/response shapes, field order, error codes, and version negotiation; KIP semantics; and the behavior JVM admin tools (`kafka-topics`, `kafka-acls`, `kafka-leader-election`, `kafka-reassign-partitions`, …) rely on are preserved without exception. **Clients must never be able to tell the broker is diskless, that a topic is also an Iceberg table, or that the WAL is also an observability backend.** When Kafka's behavior is undocumented or version-dependent, match the latest released `cp-kafka` image empirically rather than the wiki.
- **Greenfield internal freedom — no back-compat shims.** Crabka is undeployed with no persisted state to migrate and no clients pinned to a build. On-disk formats, internal enums, wire formats between Crabka's own components, and the shared substrate layout all change freely: no `#[serde(default)]` "to keep old logs readable," no `V2`-alongside-`V1` replay variants, no default-off feature-flag gating, no migration/upgrader code, no deprecated-but-kept internal surfaces. Wipe local data dirs during development. This freedom is what makes the substrate unification (Ch. 0) and the diskless internal-format changes (Ch. 1) tractable on the stated horizon.
- **Correctness/trust is a diskless SHIPPING GATE.** The classic path is already gated by Creusot-verified kernels called from production (`crates/verified`) and a `stateright` end-to-end durability model (`crates/broker/src/data_path_model.rs`). Diskless (Ch. 1) does not ship until an extended Creusot + `stateright` + Jepsen suite mechanically proves no acknowledged record is ever lost across the WAL→flush→offset seam. Lakehouse (Ch. 2) carries an analogous consistency obligation: Iceberg table state must provably match Kafka topic state across retention, compaction, aborted transactions, tombstones, and schema evolution. Correctness is a gate on GA, not a follow-up.
- **Efficiency is a continuous track.** The `sendfile`/kTLS/decode-free core (Ch. 0) is a named, benchmarked subsystem measured against `cp-kafka` via `crates/bench-driver`, not a one-time task. io_uring, production mmap, and a buffer pool remain open and are gated on both benchmark evidence and a resolution of the `unsafe_code = "forbid"` policy. Every chapter's cost/latency claims (inter-AZ bytes, ack latency, storage duplication) are validated by measurement.

## Sequencing & dependency view

This ordering is **directional, not dated**. It reflects genuine technical dependencies, not a delivery schedule.

The load-bearing insight is that **building diskless forces the shared substrate into existence**, and once topic data lives as columnar files on object storage, lakehouse and cross-signal-to-topic query fall out comparatively cheaply. Concretely:

1. **Chapter 0 (Substrate & Efficiency Core) underpins everything.** The efficiency core keeps Kafka-wire parity while the internals change beneath it, and the extracted shared-substrate crate is the single object-store read/write path that Chapters 1–3 all reuse instead of forking. Efficiency work (bench harness, kTLS-done, io_uring/mmap/buffer-pool decisions) proceeds continuously and in parallel with the rest.
2. **Chapter 1 (Diskless) is the flagship and the forcing function.** It is sequenced first among the new faces because implementing it *requires* the shared WAL, the batched object-store flush, and KRaft-coordinated stateless offset assignment — which is precisely the substrate that Chapters 2 and 3 then consume. Diskless is gated by the M3 durability proof before GA.
3. **Chapter 2 (Lakehouse) falls out of Chapter 1.** Once diskless makes topic data live as columnar files on the shared substrate, the topic→Parquet materializer, the Iceberg manifest layer, and in-process DataFusion SQL are a materialization-and-catalog problem, not a second storage system. Chapter 2 is **structurally dependent** on Chapter 1's substrate fusion; if that slips, the materializer has nothing columnar to write into.
4. **Chapter 3 (Unified Observability) is integration-led and largely parallelizable — with one gated payoff.** The four backends, four query engines, self-observability, and the demo already exist, so productization (arc steps 1–2) and the Grafana correlation wiring (arc step 3a) can proceed *now*, in parallel with Chapters 0–1, independent of the lakehouse. Only the headline cross-signal-to-topic join (arc step 3b) is **transitively gated on Chapter 2** landing topics-as-`TableProvider`.
5. **Chapter 4 (Serverless Event Mesh) is a consumption layer, largely parallelizable now — with one gated synergy.** Most of it rides surface already built: Facet 1 conformance (wire-compat), the CloudEvents binding (gateway seams + record headers), stock-KEDA consumer-group validation, and — crucially — **the share-group→KEDA backlog bridge, the one real wedge, because `DescribeShareGroupOffsets` (HWM−SPSO) is already implemented and JVM-validated**. None of that waits on Chapter 1. Only the **diskless ↔ scale-to-zero synergy** (seconds-scale broker elasticity paired with event-driven scaling) is transitively gated on Chapter 1, since brokers are `StatefulSet`+PVC pets today.

Net dependency chain: **Ch. 0 substrate/efficiency → Ch. 1 diskless (forces the substrate) → Ch. 2 lakehouse (falls out of the substrate) → Ch. 3b cross-signal-to-topic query (needs Ch. 2)**, with **Ch. 3a observability productization + correlation** and **Ch. 4 serverless event mesh (CloudEvents + KEDA share-group autoscaling) both running largely in parallel now** off the already-built stack, only **Ch. 4's diskless↔scale-to-zero synergy** transitively gated on Ch. 1, and **Ch. 0 efficiency running continuously** underneath all of it.

**On the "all-in-one is a trap" objection.** Four faces competing against four specialized, mature incumbents (WarpStream/AutoMQ on diskless; Redpanda on throughput and Iceberg Topics; Confluent Tableflow on lakehouse; Grafana LGTM+Pyroscope on observability) from a pre-GA greenfield codebase invites the "master of none" critique — and it should be met directly rather than by implying a simultaneous win on every front. The answer is the diskless-first sequencing above: the faces are not four competitive fronts opened at once but a **substrate-driven emergence** — build the shared columnar object-storage substrate to ship diskless, and the other faces become materializations of that one substrate. On each individual face Crabka concedes parity-or-behind against its specialist. The two things no incumbent has, and where the defensible wedge actually lives, are the **shared substrate** (one bucket, one DataFusion engine spanning topics and all four signals) and the **formal-durability gate** (machine-checked no-acknowledged-loss before diskless GA). The consumption layer (Chapter 4) fits the same stance: it concedes parity on three of four facets (Knative backing, CloudEvents-over-HTTP, Knative-Serving packaging) and its one wedge — share-group backlog autoscaling — is a **timing/integration first-mover**, not an inventive primitive, since share groups are a Kafka KIP rather than Crabka-proprietary.

## Non-goals

Explicitly out of scope, permanently or for this horizon:

- **ZooKeeper mode** — permanent non-goal. Crabka is KRaft-only.
- **ZooKeeper→KRaft migration** — permanent non-goal. No migration tooling, no dual-mode bridge.
- **On-disk / internal-format backward compatibility** — no migration shims, no versioned-replay enum variants, no `#[serde(default)]`-for-old-logs, no one-shot upgraders. Internal formats change freely; local data dirs are wiped during development. (Kafka *wire* compatibility is the opposite — inviolable.)
- **JVM-internal parity** — Crabka matches Kafka's observable wire behavior and JVM-tool-facing semantics, not the JVM broker's internal architecture, threading model, config surface, or on-disk layout. Where Crabka's internals differ (diskless WAL, columnar substrate, io_uring), that is by design and invisible to clients.
- **Beating specialized incumbents on their own single axis as the goal** — the goal is not to out-throughput Redpanda on raw MB/s (a stretch goal blocked by the `unsafe` policy), nor to out-feature any one specialist on its home turf. The goal is the shared-substrate unification and the formal-durability gate.
- **Shipping any new face before its correctness gate is green** — diskless does not ship on an unproven durability seam; lakehouse does not ship on inconsistent Kafka↔Iceberg state. "Ship nothing" beats "ship a byte-identical wire that silently loses acknowledged data."
- **Reimplementing the Knative control plane** — Crabka is the *data plane* (the Kafka behind Knative Eventing). It does not reimplement Knative's reconcilers, the Serving/Eventing controllers, or the Knative APIs; it satisfies the surface `eventing-kafka-broker` and KEDA already consume.
- **Forking or vendoring `eventing-kafka-broker`** — Chapter 4's Facet 1 validates the *upstream* project against Crabka as an interop/CI effort, not by maintaining a fork. Any conformance failure is fixed as a Kafka-wire-compat bug in the existing broker, never by patching upstream.
- **Making the stateful core serverless** — the broker and KRaft controller are categorically ineligible for Knative Serving (`StatefulSet`+PVC, quorum identity), and write-path observability roles (distributor/compactor/ruler) are scalable `Deployment`s that must **not** scale to zero or ingest/compaction silently stops. "Crabka on Knative Serving" means only the stateless faces (gateway, schema registry, observability *queriers*) — a deployment property of a well-factored codebase, not a differentiator.
